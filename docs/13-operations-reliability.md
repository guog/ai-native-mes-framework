# 第 13 章 · 部署、运维与可靠性

**状态：** 规格草案。**ADR：** 006、013～016、023、038、046、057、067、077、092、098～099、105、107～109、112～114、119～120、124、126～129。

## 13.1 两级部署模型

**标准部署**：Linux + Docker，MES 主应用可单实例；关键生产数据仍跨独立故障域同步持久化（数据库同步副本或认证高可靠存储），允许人工恢复，**RTO≤4 小时**。不能把“单应用节点”等同“单份关键生产数据”。

**高可用部署**：工厂内部应用/数据库节点可恢复故障，保护单一权威数据库写入，**RTO≤15 分钟**。覆盖服务器、应用实例和数据库节点故障；完整机房灾难按独立灾备方案，不混入默认 HA 承诺。是否采用不同产品 HA 功能及基础设施，按认证组合决定。

两个等级均要求关键已确认生产事务在认证故障范围内零丢失；未认证组合不能对外宣称满足目标。

## 13.2 单一写入权威与拒写

- 数据库仲裁、隔离旧主（fencing）和故障切换由经过认证的数据库/存储基础设施承担；MES 不自研多数据库主备选举。
- 只有当前可证明满足同步持久化条件时，MES 才能确认**新的关键业务写入**。持久性失效时，拒绝其成功确认，保留安全只读及非关键业务；可观测性报告当前降级模式。
- 连接丢失且提交结果不确定时，采用稳定业务请求 ID 核查执行记录后恢复，禁止直接重放新事务。
- 故障切换后，核验业务数据、关键审计、幂等执行记录、Outbox 和 Worker 租约一致性；恢复生产写入前须达到认证的读写就绪条件。

## 13.3 备份、恢复及升级

- 即使使用同步副本，也必须保留独立备份及恢复演练：复制不能代替防误操作、数据损坏或逻辑错误的备份。
- 应用、数据库结构、插件包和声明式配置均有版本标识及可追踪发布记录。升级前检查版本、空间、数据库兼容性、迁移及可恢复备份。
- 使用 Expand–Migrate–Contract 阶段性兼容迁移。破坏性迁移走维护窗口，不假定自动逆迁移能无损恢复业务数据。
- 生产插件安装及升级由授权人员最终批准；成功通过 CI 不等于获准上线。
- 集团断网不能阻止工厂本地登录、关键生产事务与本地审计。AI Runtime 故障允许降级。

## 13.4 运维能力与 SLO

需具有健康和就绪检测、服务与数据库连接状态、同步副本持久性状态、插件状态、队列积压、Outbox 年龄、同步检查点、空间阈值、异常失败任务、审批积压、结构化追踪等运行指标。

项目须配置硬件、数据量、离线事件率和最长离线时长，建立存储容量和告警阈值；关键事件不得被静默丢弃。P95/吞吐指标以 ADR-128 的参考负载为来源，未经测试不得写成达标。

## 13.5 故障注入与认证证据

对于每个数据库×框架版本×部署模式的认证组合必须演练：主节点损毁、网络分区、提交中断、失去同步副本、故障切换、恢复、脑裂隔离，以及审计/Outbox/任务重放。

记录故障起点、最后确认的业务请求 ID、恢复完成时刻、写入不可用时长、受影响数据库事务及核验结果，才能判定 RTO 和零丢失目标。

**未完成项：** 四数据库具体版本、驱动版本、拓扑和同步持久性认证证据，标准参考硬件与 P95 指标、离线目标时长尚待填充；这些都是待验证/待量化，不得伪造。


## 13.6 故障域与部署审批清单

标准部署必须明确应用节点、关键数据主副本、同步确认点、备份存储和运维入口所在的实际故障域；两份数据如果仍依赖相同的不可恢复存储、电源或管理平面，不能因为节点数为二就宣称满足 ADR-126。高可用部署还要明确数据库独立仲裁或隔离的实现方案，以及自动切换条件和人工接管方式。

计划内发布应遵循运行前健康检查、发布包/迁移版本匹配、按节点渐进就绪、异常拒写保护、验证完成再接受关键生产流量。日志、监控、审批系统和集团网络故障的依赖优先级应与本地生产关键事务分开，不能让非关键监控故障导致已认证的数据库状态被误判为可写。

## 13.7 运行手册至少包含

- 主节点故障时如何判断旧主已隔离，是否允许备用提升，何时允许重新接纳写请求。
- 提交结果不确定时按稳定 requestId 定位，禁止先删幂等记录再重试。
- 同步积压导致磁盘告警时如何限流非关键任务、扩容和保留关键事件。
- 安全升级失败时恢复代码、Schema 快照和运行配置，若数据迁移不可逆则走已批准修复流程。
- 性能回退或 AI Runtime 不可用时仅降级相应能力，不把所有 MES 功能一并中断。
