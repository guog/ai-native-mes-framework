# 第 14 章 · AI Native 软件工程体系

**状态：** 规格草案。**ADR：** 004～005、028、037、059、080～081、087、096、100、104。

## 14.1 目标及边界

AI Native 研发意味着 Code Agent 能**读取架构约束—理解契约—生成变更—自动验证—提交审核**。不能把大量提示词等同于工程约束，也不能允许 Agent 直接把未经评审的扩展安装到生产 MES。

框架、官方模块、SDK 和示例应用采用统一 TypeScript Monorepo；客户插件可独立仓库。每个模块的公开输入/输出 Schema、所有权、依赖、权限和测试要求应成为版本化的机器可读规格，而不只是自然语言段落。

## 14.2 面向 Agent 的文档层次

- **架构基线**：`adr/` 与主规格书，冻结版本号及变更治理。
- **机器可读契约**：模块 Manifest、业务动作 Schema、GraphQL 读取契约、事件和任务版本、数据库支持声明、UI 展示元数据。
- **工程约束**：公开 API 边界、依赖无环、关键写入路径、迁移策略、插件权限、测试禁区和回归要求。
- **任务工作单**：需求→验收标准→涉及模块/ADR→允许修改的文件范围→需要运行的质量检查→风险与人工审批点。
- **验证证据**：静态依赖检查、契约差异比较、接口单元/集成测试、四数据库功能兼容、安全负向测试及变更清单。

## 14.3 变更工作流（规范，不是自动化脚本）

1. Agent 读取需求、相关 ADR、模块契约及测试基线；说明不确定或冲突约束。
2. 提议变更边界和相关契约差异；不能将架构破坏性变化当作小补丁隐式提交。
3. 生成代码、声明性元数据、迁移计划和测试；代码只使用公开模块依赖。
4. 自动验证 TS/Schema、依赖无环、GraphQL schema 兼容、动作幂等、授权、审计、版本升级、数据库迁移等质量门禁。
5. 人工审查受影响权限、关键业务状态、破坏性数据库变更和面向生产的发布清单；CI 通过但未审批不得正式上线。
6. 版本化发布签名包，经最终授权者批准安装/升级，保留审计和回退/恢复计划。

## 14.4 必须自动检查的架构纪律

- 禁止跨模块访问私有源码或私有数据库表；静态模块依赖无环。
- 每个新增 GraphQL Mutation 必须映射权威动作契约；重要 Query 明确字段/工厂级授权和复杂度预算。
- 生产关键动作需要稳定请求 ID、业务幂等、关键审计；需要审批的动作必须绑定参数与资源版本。
- 插件不能未经签名、权限授予和兼容性验证热安装；低信任扩展保持进程/前端隔离。
- 数据库变更不能绕过四库兼容窗口；客户插件需要声明目标数据库；迁移必须预检。
- 测试报告必须区分“编译通过”“单库集成通过”“多库契约通过”“故障认证通过”，不能混淆。

## 14.5 实施切入点

建议使用一个纯测试用途的参考业务模块，不把业务场景硬编码进框架内核。其目的是让 Agent 开发体验、事务、GraphQL、Worker、Outbox、迁移及审计在稳定基线上获得验证；这是 ADR-128 已确认的能力。

**不属于当前文档阶段：** 创建实际 TypeScript Monorepo、编写 SDK/自动化流水线、选择某个 Code Agent 厂商作为唯一工具、实现参考模块；均留待正式工程阶段。


## 14.6 人与 Agent 的职责分工

Code Agent 可自动生成可审查的业务模块变更，但架构违规、数据库不可逆迁移和生产授权策略改变必须被 CI/审核阻断。对于不确定的业务需求，Agent 应输出待确认假设而不是自行补造关键业务事实。所有生成产物应标明模块所有者、影响的 ADR、改动的公开契约、测试证据和回退限制。

统一评审单的最小信息：原始需求、业务验收情境、修改范围、模块/动作版本差异、数据库/四库影响、安全影响、自动测试、已知风险、发布审批。运行时 AI Agent 调用业务动作的权限不能作为开发 Agent 发布生产插件的授权来源。

## 14.7 文档与代码间的一致性治理

规格冻结后，可进一步把架构规则转成可执行校验：模块 DAG 无环、禁止内部 import、契约字段版本核对、GraphQL 查询权限声明、业务动作审计和幂等要求、插件能力权限变更审查。但目前只定义验证输入/预期，不编写校验程序。任何 Code Agent 对 ADR-001～130 的冲突建议必须以候选变更提案单独提出，不得隐式更新基线。
