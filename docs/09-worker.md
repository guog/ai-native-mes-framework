# 第 9 章 · 持久化任务与独立 Worker

**状态：** 规格草案。**ADR：** 034、040、045、049、061、074、082、092、118、121～122。

## 9.1 定位

框架统一提供持久化任务契约，独立 Worker 执行；默认复用实例主业务数据库作为最小任务存储，不强制加入 Redis、Kafka 或独立消息平台。Worker 可以与 MES 部署于一台机器，但采用独立进程。任务系统服务于业务异步处理、插件任务、Outbox 投递、补传及维护工作，不替代实时设备控制。

## 9.2 任务契约

持久化任务元信息应包含稳定任务 ID、任务类型及版本、所属模块/插件及处理器版本、所属工厂与执行身份、payload Schema 版本、生命周期状态、重试策略、可领取时间、租约持有人、租约过期时刻、代际/栅栏令牌、幂等标识、checkpoint、执行关联 ID、错误分类与失败审计。字段具体表示属草案。

任务至少一次执行，不能对任意外部副作用承诺 exactly-once；必须以幂等、副作用去重或可恢复补偿实现正确业务效果。

## 9.3 领取、续租与失败恢复

1. 在数据库中原子领取任务，并更新租约持有人、租约有效期和 fencing token；不同数据库可以使用不同的经过认证的 SQL/锁策略。
2. 执行前核验插件活跃状态、任务处理器版本、所需能力、工厂隔离与任务授权；不得凭旧队列状态绕过插件停用。
3. 长任务定期持久化 checkpoint 与进度，按必要频率续租；旧 Worker 租约失效后的提交必须经过状态版本比较，否则拒绝持久状态推进。
4. 任务失败分类：可重试临时故障、不可重试输入/权限故障、业务冲突待人工、重试次数耗尽隔离。
5. 进程重启后扫过期租约恢复领取，但必须查询幂等结果并避免重复外部副作用。
6. 插件 draining 时不接受新任务领取，在途安全结束或检查点保存，旧处理器不可用时保留任务并标记待恢复。

## 9.4 数据库一致性与 Outbox

- 同一业务事务中需要创建的任务/事件记录，在主库事务提交后对 Worker 可见。
- Outbox 投递可以重发；接收端按事件 ID 幂等消费。`sent` 状态不是全局恰好一次的证明。
- 危险的外部系统操作通过独立受控业务动作、审批及幂等键防止重复执行。

## 9.5 验收场景

- 两个 Worker 抢占同任务：同一租约只能由一个所有者有效推进；租约过期时旧执行者不能重复提交权威状态。
- 执行完业务副作用但记录完成前崩溃：通过业务请求 ID 恢复，不重复生产效果。
- 主库切换与 Worker 全部重启：任务可恢复领取，持久执行结果一致，关键审计不丢失。
- 插件升级或停用期间队列含旧处理器版本：任务安全暂停或使用兼容处理器，不被丢弃。
- PostgreSQL、SQL Server、MySQL、达梦分别验证领取/续约/死锁/超时/锁重试等行为。

**待验证：** 四数据库租约策略、任务吞吐和数据库负荷、轮询频率、批量领取数量及 HA 资源竞争。由 ADR-128 的参考模块统一测量。


## 9.6 Worker 内部责任边界

任务调度、租约状态、插件处理器注册、失败分类和执行结果存储分别应具有明确拥有者；任务不能通过任意 SQL 字符串注入处理器。任务载荷需要版本化，并保留能够让旧版本恢复或迁移的明确兼容窗口。Worker 运行身份必须按工厂/模块作用域授权，禁止因队列消费者拥有数据库写权限而跳过生产关键业务动作的执行控制。

对于事务性业务出站事件，Outbox 读取与推送属于 Worker 的一种受控职责；发送成功不是接收方业务持久化成功。任务状态标记已完成之前，至少需要获得目标系统契约要求的确认。在途 Worker 崩溃后，如果无法判定外部副作用是否执行，应查询稳定请求 ID 或进入人工核查，而不是盲目重复危险动作。

## 9.7 容量和诊断约束

至少观测任务排队深度、最早未处理时间、成功/失败/重试比、最长锁持有、租约失效率、重复领取次数、数据库等待时间和 Worker CPU/内存。高可用多个 Worker 发生抢占、网络分区或时钟误差时，不能仅依赖进程内互斥锁保证正确性。测试必须覆盖租约过期的迟到 Worker、节点升级前后的处理器混用和数据库主备切换。性能基准应同时测量 Worker 峰值与正常 API 的互相影响。
