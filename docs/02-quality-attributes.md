# 第 2 章 · 质量属性与架构约束

## 2.1 优先级与验证原则

关键生产数据正确性 > 能力完整性/可用性 > 系统简单性与运维成本 > 性能极限。此处表达架构取舍优先顺序，不代表可以忽略生产现场的可用性要求。指标必须说明故障域、测量方法、判定条件和认证的数据库/部署组合。

### 可靠性指标（已确认）

- **关键生产事务 RPO 目标**：零已确认提交丢失。含义是成功确认的关键事务不得在认证覆盖的故障场景下消失；尚未给出所有底层组合的实现证明。
- **标准部署 RTO**：≤ 4 小时。可单应用实例，但关键数据必须跨独立故障域同步持久化，允许人工恢复。
- **高可用部署 RTO**：≤ 15 分钟。覆盖工厂内部单应用/服务器/数据库节点故障；跨机房灾难由独立灾备方案处理。
- **派生数据**：可丢失后重建；权威原始数据仍根据数据等级设定持久性。派生数据的具体重建时间待按负载评估。
- **故障失去持久性保证**：新的关键写入不得得到成功确认；允许安全的只读及非关键能力继续运行。
- **数据库 HA**：只能有一个权威写入方；晋升备用节点之前需经仲裁和旧主节点 fencing。由已认证基础设施实现，MES 负责检测/重连/拒写/恢复/审计。

### 典型验收场景（规格草案）

1. 关键事务提交成功后，杀死应用进程：恢复核对业务、幂等执行记录和审计，必须一致。
2. 关键事务提交确认前切断网络：客户端重试同一稳定请求 ID，系统应可核查未知提交结果，不能重复记账或报工。
3. 数据库主节点不可恢复失效：检查故障恢复、已确认提交、单权威节点及时间指标。
4. 同步故障域失联：关键动作不再返回成功；安全查询和非关键功能根据依赖情况继续。
5. 工厂离线积压超过设定阈值：系统预警，关键事件不得静默丢弃，恢复后按检查点可靠补传。

## 2.2 一致性

- 关键业务状态、关键审计和 Outbox 待发送事件应在**同一本地数据库事务**中原子提交。
- 消息至少一次交付，接收端业务幂等；按业务实体维护必要顺序，不能宣称分布式严格 exactly-once。
- Worker 至少一次执行；锁租约和处理器重复副作用都要由独立验收场景验证。
- 工厂本地数据为生产事务权威；集团不能跨站点直接提交工厂生产事务。
- 提交结果不确定时必须使用同一业务请求 ID 查核并重试，禁止每次重试生成新的业务身份。

## 2.3 安全

- 用户及后台 Agent 双执行身份，分别审计授权来源。
- 本地用户认证和授权在断网时可运行；权限定期同步、版本化与本地紧急撤销。
- 低信任插件独立执行、最低数据库权限、文件/网络/CPU/内存限制；生产关键状态必须经受控动作修改。
- GraphQL 既要入口授权，也要应用服务、字段和资源级授权；要求工厂数据隔离。
- AI 动作发现只是能力查询，执行时再次校验权限、审批、资源版本和有效期。
- 生产签名插件包的发布由授权人员最终批准。

**负向测试**：跨工厂越权读取、非法动作调用、绕过审批、失效授权继续执行、插件绕过受控关键写入、恶意或故障插件影响其他模块、GraphQL 高复杂度查询影响关键生产业务。

## 2.4 性能与容量（数值待确定）

- 负载基线需要覆盖 GraphQL Query/Mutation、业务事务、审计、Outbox、Worker、跨站点同步。
- 由仅用于测试的参考业务模块生成可复现负载，不纳入产品的正式 MES 业务范围。
- 需要在规定硬件/数据规模/数据库/部署形态下明确：并发连接、吞吐量、Query/Mutation P95、Worker 恢复延迟、Outbox 积压/同步吞吐、最长断网积压容量。
- **未确认具体数值，不得自行设定一个默认 P95 作为最终承诺。**

## 2.5 易维护性与 AI 可开发性

- TypeScript Monorepo 集中框架内核、SDK、官方模块与应用；客户插件可独立仓库。
- 模块依赖无环，仅引用公开契约，不直连其他模块私有数据/实现。
- 所有面向 Code Agent 的关键架构规则、Schema、测试约束和工作指引均与代码仓库同步版本化。
- Code Agent 代码必须经过架构规则、权限、迁移和契约/自动化测试，生产交付还必须经人工批准。

## 2.6 数据库认证

- 功能认证与 HA 认证分别执行。
- 认证矩阵维度：数据库产品及大版本、驱动版本、框架版本、标准/高可用部署模式、验证场景。
- 对每个正式认证组合进行节点故障、网络分区、提交中断、切换恢复测试。
- 达梦 Kysely Dialect 未认证时不得按“已支持”宣传，必要时评估受控 dmdb/SQL 替代路线。
